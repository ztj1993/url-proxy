# 方案与特性规范标准 (Plans & Features Specification)

## 1. 目标与定位 (Objective & Scope)
本规范用于标准化 `url-proxy` 项目方案文档（Plans）的编号规则、结构分层、撰写原则与维护机制，确保技术文档体系清晰、内聚、可演进，并消除因代码重构和目录调整带来的历史文档包袱。

---

## 2. 编号与层级规范 (Numbering & Hierarchy)

所有方案文档统一存放在 `docs/plans/` 目录下，采用三位数字前缀与单层平铺命名规范：`<编号>-<英文语义名>-{zh,en}.md`。

### 2.1 阶段主方案 (Master Plan: xx0)
- **编号格式**：末尾为数字 0（如 `100`, `200`, `300`, `310`, `320` 等）。
- **定位与职责**：
  - 扮演该演进阶段的顶层引导方案；
  - 阐述该阶段的业务背景、核心痛点、建设目标与顶层架构决策；
  - 提供该阶段下属子方案的演进矩阵与实施规划表格；
  - 规定该阶段引入或变更的全局配置规范与协议支持。
- **演进步进**：下一个重大功能/阶段方案按 `+10` 递进（如 310 演进至 320，后续为 330）。

### 2.2 子方案与特性 (Sub-plan / Feature: xx1 ~ xx9)
- **编号格式**：末尾为非零数字（如 `101`, `102`, `301`, `311`, `321` 等）。
- **定位与职责**：
  - 隶属于对应前缀的阶段主方案（如 311~318 隶属于 Plan 310）；
  - 聚焦于单一功能特性或独立架构模块的详细技术方案与协议行为机制；
  - 详细定义参数语法、执行流程、边界条件处理及自动化验证标准。

---

## 3. 核心撰写与解耦原则 (Decoupling Principles)

为避免文档随代码重构或目录演进而产生破损链接与维护包袱，方案文档必须严格遵守以下原则：

### 3.1 严禁绑定源码物理文件路径
- **禁止硬编码源文件路径**：方案文档属于架构与设计层规范，严禁在正文或标题中硬编码具体的代码文件相对路径（如 `.go`、`.c` 等具体源文件路径）。
- **统一使用逻辑模块与抽象领域命名**：指代系统实现时，必须使用逻辑架构概念或抽象模块名称，例如：
  - “统一配置引擎” 或 “配置模块 (Config)”
  - “缓存管理模块 (Cache)”
  - “并发下载合并模块 (Downloader)”
  - “响应体重写引擎 (Rewriter)”
  - “协议代理与调度核心 (Proxy)”
  - “服务主装配入口 (Main Entrypoint)”

### 3.2 严禁方案间包含跨文档跳转超链接
- **避免硬编码 Markdown 相对链接**：方案间禁止使用形如 `Feature 311 (path/to/311-xxx.md)` 或 `304 规范 (path/to/304-xxx.md)` 的文件跳转链接，防止未来文件名微调或路径变迁引发批量死链。
- **统一使用文本/行内标记代号引用**：跨方案引用时，统一使用规范代号与名称进行纯文本指引，例如：
  - `Feature 311 (响应体流式动态重写引擎)`
  - `Feature 304 (统一代理配置文件系统)`
  - `Plan 300 阶段`

### 3.3 路径与格式合规准则
- **严禁输出绝对路径与协议链接**：文档中严禁出现宿主机绝对路径、盘符路径、WSL 挂载路径或 `file://` 协议链接。
- **配置与资源使用项目相对路径**：涉及配置文件或测试套件时，统一使用相对路径（如 `proxy.conf`、`tests/304_unified_config/`）。
- **代码文件与符号不包裹超链接**：文档中提及文件或符号时，统一使用行内代码格式标记（如 `proxy.conf`、`url-proxy`），严禁包裹任何超链接。
- **中英双语强制配对**：所有方案文档必须同时维护中文（`-zh.md`）与英文（`-en.md`）双语版本。
